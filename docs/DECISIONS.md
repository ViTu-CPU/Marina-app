# Design decisions and assumptions

Each entry: what was decided, why, and who decided it. "Owner" = decided by the project
owner; "Default" = chosen by the implementer under SPEC §0 (simplest extendable option).

## Decided by the owner (2026-11-13)

| # | Decision | Notes |
|---|---|---|
| D1 | Display: lengths in m with 1 decimal; areas (m²) and counts as integers. | Follows SPEC §3. `CLAUDE.md` updated to match. |
| D2 | **Uniform pier pitch per layout** (strategies A–D), derived from the longest boat class with `share > 0`. | SPEC §5.3 makes the pitch depend on the longest boat in the adjacent rows, which is only known after filling. Per-pier size zoning (variable pitch) is postponed to a later strategy. Known cost: wastes water when the mix contains few large boats. |
| D3 | `BoatClass.share` is the target fraction of the **berth count**. It is a target, not a hard constraint; the deviation from the target mix is reported in the stats. | An objective such as "Max capacity" must not fill everything with the smallest class. |
| D4 | Strategy D (shore-parallel pier): the main pier runs **along the shoreline, touching it**, with fingers and berths on the water side only. | Satisfies the "every main pier connects to the shoreline" check (SPEC §6) without modelling a gangway. |
| D5 | New parameter `Params.shoreOffset` (m, default 0): distance from the shore end of a pier to the first finger/berth. | Extension of the SPEC §4 data model. |
| D6 | GeoJSON import (SPEC §3.3) and local refinement (SPEC §5) are **not** part of the first working version. | To be revisited once the Definition of Done is met. |
| D7 | `CLAUDE.md` lives in the repository root. | |
| D8 | Static build uses relative asset paths (`base: './'`). | Hosting target not yet chosen. |
| D9 | Work is committed task by task directly to `main`. | |
| D10 | **Size zoning (2026-11-13):** in addition to the uniform module of D2, the generator produces a layout in which every row is sized for its own boats — strategy **E**. D2 still applies to strategies A–D. | The uniform module wastes water when the mix has a few large boats. Details in I23–I27. |
| D11 | **Unreachable berths (2026-11-13):** left out of the calculation, but the number is shown in a warning and in the statistics. | See I14. |
| D12 | **A layout with berths left out is not "constraints met" (2026-11-13).** It carries the warning `BERTHS_LEFT_OUT_UNREACHABLE`, so its status is `geometricOK` (amber), not `operationalOK` (green). Supersedes the first version of I14, where the count was only a note. | The pier layout could not be used as intended; the user should see that at a glance. |
| D13 | **Strategy B (2026-11-13):** the reading recorded in I12 is accepted. | |
| D14 | **Online map background (2026-11-13):** OpenStreetMap tiles can be shown under the drawing, so a background image need not be loaded and calibrated by hand. Chosen over the National Land Survey's aerial photos because it needs no API key. | Part of SPEC Phase 4 ("real geographic coordinates and map tiles"), brought forward at the owner's request. Details in U14–U17. |
| D15 | **Sources (2026-11-14):** RIL 201-3-2013 and AS 3962 are paid and not available; use public sources only (manufacturer data, theses, public guidelines). Values that should come from those standards are marked "to be verified". | Background and sources in `docs/RESEARCH.md`. The tool never states compliance (CLAUDE.md). |
| D16 | **Water depth (2026-11-14):** one design depth per project (plus water-level range), no soundings. | Anchoring is a preliminary quantity estimate. |
| D17 | **Winter (2026-11-14):** pontoons stay in the water over winter. | Default products are heavy concrete pontoons; ice loads are not computed and are flagged as a warning. |
| D18 | **Prices (2026-11-14):** unit prices are VAT 0 %; VAT 25.5 % is added to the total and shown separately. Supplier prices published with VAT are converted (÷ 1.255). | Contractor practice. |
| D19 | **Price file (2026-11-14):** the prices and calculation parameters live in an Excel file in the repository that the user can edit. | Requested by the owner. |
| D20 | **Target counts (2026-11-14):** the boat mix can be given as a target **number of berths per class** instead of shares. | Owner request. Details in I31–I34. |
| D21 | **Access pontoon (2026-11-14):** empty pontoon metres can be placed, e.g. in front of a quay wall too high to step down from, and main piers ("pistolaiturit") start from it. | Owner request. Details in I35–I38. |
| D22 | **More manual editing (2026-11-14):** fill one side of a pier with one boat class or the mix (with empty metres at the shore end), change a berth's class, change a pier's length, delete a pier, add a pier. | Owner request ("assign pier sides to one berth type", "add/remove berths"). Details in I39–I43. |
| D23 | **Anchoring plan (2026-11-14):** a preliminary anchoring plan per layout, shown as a map layer: chain lines and concrete anchors for main piers and access pontoons, for one design depth (D16). | Owner request. A quantity estimate, not a mooring design (CLAUDE.md). Details in I47–I49. |
| D24 | **Bill of materials and cost estimate (2026-11-14):** products from the price list (D19), quantities from the layout and the anchoring plan, labour and plant from output rates, VAT 0 % with VAT on the total (D18), exported as Excel. | Owner request. Details in I50–I53. |

## Defaults chosen by the implementer

| # | Decision | Why |
|---|---|---|
| I1 | Geometry library: **JSTS**, imported only inside `src/engine/geometryOps.ts` (buffer, union, difference, intersection). `src/engine/geometry.ts` holds the pure vector/polygon maths and predicates with no library dependency. | SPEC §5.1/§6 need polygon buffering. `@flatten-js/core` 1.6.15 has no buffer/offset operation (it is a separate package last published 2023-08). JSTS's bundled type declarations do not cover the operations we use, so the wrapper carries its own narrow typings. |
| I2 | Undo/redo is a hand-written snapshot history (past / present / future) over the project document only. | View state (pan, zoom, active tool) must not be undoable; keeps dependencies small. |
| I3 | No ESLint for now. Gates are `tsc --noEmit` (strict) and the test suite. | `typescript-eslint` declares peer support for TypeScript `<6.1.0` only (checked on npm 2026-11-13); SPEC does not require a linter. |
| I4 | **Pier head clearance**: a pier ends at least one fairway width before the end of the buildable water on its line, so boats can pass around the head. | Fairways between shore-connected piers are dead ends at the shore; the only way out is around the heads. Conservative when the water limit is only an administrative boundary. |
| I5 | A pier is shore-connected when its shore end is within **0.5 m** of the shoreline (tested at the centre and both corners of the pier end). | Covers drawing inaccuracy and shore edges that are not square to the pier. |
| I6 | Two regions: **structure region** = water − obstacle buffers − `noStructures` − `protected` (piers, fingers); **navigable region** = water − obstacle buffers − `noNavigation` − `protected` (berth slots, fairways). | SPEC §5.1 defines only the first. Boats may lie in a `noStructures` zone, structures may stand in a `noNavigation` zone, nothing may be in a `protected` zone. |
| I7 | **Class mix rule**: each new berth goes to the class that is furthest behind its target share (counts are tracked over the whole layout). Each contiguous run of bays is then re-ordered by boat length, shortest at the shore. | Deterministic; keeps every class within about one berth of its target; satisfies "larger boats at the outer end" (SPEC §5.5). |
| I8 | **Berth corridor**: a bay is kept only if the water from the pier edge out to `row depth + fairway width` is navigable over the bay's full width. Row depth and fairway width are those of the longest active class (D2). | Implements "every slot borders a fairway of the required width" (SPEC §6) inside the generator. |
| I9 | When no bay fits at the current position, the row cursor advances by **0.5 m** and tries again; fallbacks are tried in the order: mix-driven choice → smaller classes → fewer boats in the bay. | SPEC §5.5: "try a smaller boat class; otherwise leave it empty". |
| I10 | A row always ends with a closing finger. The boat rectangle sits at most 0.2 m off the pier edge. | Drawing assumptions; the second does not affect counts. |
| I11 | Round obstacles are approximated by a polygon that contains the circle (never smaller than the object). Buffers use 8 segments per quarter circle. | Errs on the side of keeping clear. |
| I12 | **Strategy B** places piers at **twice the pier pitch** ("every other pitch"), square to the shore, with the best offset. Pier length follows the same rules as in A (water limit, head clearance, `maxMainPierLength`), so B's piers are not longer than A's. | Checked against the specification on 2026-11-13 at the owner's request. The only definition of B is SPEC **§5.7**: "B: piers perpendicular to shore, fewer and longer piers (every other pitch)". SPEC §6 (Validation) does not mention strategies; its checks apply to B as to every layout. "Fewer" follows from every other pitch. "Longer" has no rule behind it in the specification: nothing in §4–§6 lets a pier of B exceed the limits that bind A, so it is read as a description, not a requirement. If B should really have longer piers, it needs its own parameter (e.g. a separate maximum length). |
| I13 | **Strategy C** contributes the best layouts of up to four other orientations from the sweep (the shore-perpendicular one is A). | Gives the user genuinely different directions to compare; near-duplicates are removed afterwards (SPEC §5.8). |
| I14 | **Unreachable berths are removed** from generated layouts: berths whose fairway cannot be reached from the entrance (e.g. the dead end behind a rock) are dropped together with fingers and piers left without berths. **The number left out is kept** on the layout (`Layout.unreachableRemoved`, `Stats.unreachableRemoved`) and shown on the alternative's card, in the comparison table and in the CSV export. The layout also gets one warning issue, `BERTHS_LEFT_OUT_UNREACHABLE`, with the count in its message, which makes its status `geometricOK` instead of `operationalOK` (D12). The berths themselves stay out of every total. The count and the warning are kept when the layout is edited by hand. | SPEC §5.5 keeps a bay only if it passes the §6 checks; connection to the entrance is one of them. Owner decision 2026-11-13: remove them from the calculation but show how many were left out. Piers are not shortened by this step. |
| I15 | **Search score counts reachable berths only**, estimated on a coarse grid (cell 1–2.5 m, lenient by about one cell). The exact check (polygon buffer) is run on the layouts that are returned. | The exact check costs ~10 ms per layout, too slow for ~1,700 candidates. Without it the search favoured layouts that walled off part of the site. |
| I16 | **Clear pier head**: a pier is shortened in 1 m steps until the water beyond its head is navigable for one fairway width across the pier, its rows and their fairways. | With slanted piers the rows reach the water limit before the centreline does (extends I4). |
| I17 | During the search the 'balanced' objective is approximated by capacity; the real objective is applied when the evaluated alternatives are ranked. | 'Balanced' needs the fairway area of all alternatives, known only after full evaluation. |
| I18 | Where a pier line touches the shoreline at both ends (e.g. a channel), the pier starts from the end that comes first along the line. Piers from both banks on the same line are not generated. | Simplest deterministic rule. |
| I19 | Shapes passed to the polygon overlay (fairway strips, occupied blocks) are grown by **1 mm**, and overlay falls back to snapping/rounded coordinates if JSTS throws. Fairway areas are therefore exact to well under 1 m². | JSTS's classic overlay throws a TopologyException on nearly coincident edges, and its own snapping fallback does not catch it. |
| I20 | Slots must lie in navigable water; a slot in a `noNavigation` zone is an operational warning, in a `protected` zone or an obstacle buffer a geometric error. | SPEC §6 lists only structures for the zone check. |
| I21 | Connection to the entrance is tested with a circle 0.2 m narrower than the required fairway width. | Absorbs the polygonal approximation of round buffers. |
| I22 | Local refinement (SPEC §5, "if time allows") is not implemented. | Owner decision D6. |
| I23 | **Strategy E, layout rule.** Piers are square to the shore and are placed one after another across the site. Each row is designed for the largest class that still has berths to place, so sizes go from the largest boats to the smallest. Row depth = slot length of that class; the fairway between two piers = the wider of what the two facing rows need; the pier follows at previous row edge + fairway + row depth + half the pier width. | Processing from large to small means the fairway in front of a row is always decided by the row placed before it, so no iteration is needed. Both directions across the site are tried. |
| I24 | **Strategy E, class mix.** The total number of berths is split over the classes by target share (largest remainder method) into quotas; rows are filled class by class from the largest down. The total is the largest one for which every quota is met, found by bisection. | Gives the exact target mix, unlike assigning whole piers to one class. |
| I25 | **Strategy E, classes that fit nowhere** (their own row, fairway and pier do not fit the site) are left out and the others are placed. The deviation from the target mix is reported in the statistics. | Otherwise one class that cannot be placed would hold the whole layout back (D3: the mix is a target, not a hard limit). |
| I26 | **Strategy E, pier heads.** Each pier keeps clear the fairway width of its own largest class at its head. If that leaves berths that cannot be reached from the entrance (large boats having to pass the narrower heads of small-boat piers), the variant with the largest class's fairway width at every head is also tried. | Narrow heads give longer piers for small boats; the reach check decides whether they work for the site's entrance. |
| I27 | **Strategy E, search.** Start offsets are swept in 2 m steps over one module of the largest class. They are first ranked by how many berths get placed when more are asked for than can fit; the exact search (bisection) is run for the six best per direction. | Keeps the strategy within the time limit. A better start offset can be missed. |
| I28 | **Search speed-ups that do not change the result:** (a) a candidate is skipped when its piers, both sides full at the average pier length per berth plus two berths per row, cannot reach the best count so far; (b) the reach test is skipped when the berths placed are already too few. **One that can:** (c) strategy C first sweeps every orientation with offsets 4 m apart and runs the 1 m sweep only for orientations within 25 % of the fourth best. | SPEC §10 asks for under 2 s. With (c) an orientation whose best offset lies between coarse steps and gains more than 25 % could be missed; the returned layouts are always swept at 1 m. |
| I29 | When nothing fits, the diagnostic compares the site with what the **least demanding boat class** needs (was: the longest class). | With strategy E a site is usable as soon as one class fits. |
| I30 | Strategy E is not produced when only one boat class has a share above zero. | It would equal strategy A. |
| I31 | **Target counts are upper limits.** With `Params.berthTarget = 'count'` each class gets at most its count; the classes are interleaved by the shares the counts imply (I7), and filling stops when every count is used up. Berths short of the counts are shown as `Stats.targetShortfall` (card, comparison table, CSV) but are **not** an issue, so they do not change the status. | A demand ("we need 20 berths for 7 m boats") is not a constraint of the site (D3). Placing more than asked would waste pontoon. |
| I32 | **The pier on which the counts run out is made as short as possible:** the shortest length in 0.1 m steps that still takes the same number of berths (bisection), so both sides share them instead of one side being filled first; then shortened to the end of its last bay. Strategy E only gets the second step. | Without it the last pier kept its full length with one half-empty side. |
| I33 | With counts, 'minInfrastructure' measures its shortfall against the total of the counts instead of the separate berth target. | One target, not two. |
| I34 | Switching to counts for the first time fills them from the preferred (or first) alternative, or from the shares of 100 berths when there is none. Older project files open with shares and zero counts. | Gives a sensible start; files stay readable. |
| I35 | **An access pontoon is part of the site**, drawn by its centreline (two clicks) with its own width (default: main pier width). Main piers may start from either long edge (tolerance as I5). The pontoon is taken out of the structure and navigable regions, so nothing else is built on it and boats cannot pass through it; validation treats it like a structure (inside water, clear of obstacle buffers and restricted zones, no overlaps, fairways not obstructed). It carries no berths. | Site element because it is input to the generator, not one of its results. |
| I36 | The access pontoon's length and deck area count in the pontoon metres of **every** layout (`Stats.accessPontoonLength`). | It is built whichever layout is chosen. |
| I37 | An access pontoon more than **12 m** from the shoreline gets a warning: Marinetek states access bridges of "4–12 m lengths" (docs/RESEARCH.md §2.1). | Reaching it needs a gangway. |
| I38 | Drawing and editing an access pontoon does not snap to the site. | It lies off the wall on purpose; snapping pulled it onto the shoreline. |
| I39 | **Filling a side** replaces all berths and fingers on that side by a fresh fill with the generator's row filling (I7–I10), using only the chosen class or the project's mix; the bays start `emptyLength` m from the shore end (default `shoreOffset`). The fill is kept clear of the site's obstacles and zones and of every other pier, finger and slot of the layout. | Reuses the generator's checks, so a manual fill is as valid as a generated one. |
| I40 | A fill **never takes the fairway** another row's berths need in front of them: new berths whose slot lies in such a fairway are dropped, with fingers left without a berth. | Filling one side must not break the rows already there. Found in the browser test. |
| I41 | With the mix, the classes follow the targets counted over the whole layout; target counts are **not** applied as limits in manual edits. | The user asked for that side to be filled; the shortfall statistic still shows the result. |
| I42 | **Changing a berth's class** keeps the slot's start along the row and its position at the pier edge; the slot gets the new class's size. A wider boat therefore shows up as an overlap issue instead of moving its neighbours. | Transparent; the user can fill the side again. |
| I43 | **Changing a pier's length** keeps the shore end and deletes fingers and berths that would end beyond the new head (rounded to 0.1 m). Deleting or resizing a locked pier is not possible. | Same rule as moving (U1, U2). |
| I44 | **Price list file:** `data/hinnasto.xlsx`, sheets *Instructions*, *Products* and *Parameters*, header row with fixed column keys (order free, unknown columns ignored). Read and written by a small own module (`src/catalog/xlsx.ts`, zip via `fflate` 0.8.3) instead of a spreadsheet library. Checked with openpyxl and with a copy re-saved by LibreOffice, which reads back identically. | ExcelJS 4.4.0 is about 22 MB unpacked and the npm release of SheetJS (0.18.5) is outdated; the price list only needs plain tables. |
| I45 | Each product row keeps the **price exactly as published** and whether it includes VAT; the tool converts to VAT 0 % with `vat_pct` (D18). A calculated VAT 0 % column is written for the reader but never read. Rows with no public source carry "ESTIMATE" or "Assumption" in the note (e.g. Marinetek per-metre prices, work-boat day rate, all labour productivity figures). | Traceability; the owner asked for prices "based on information as accurate as possible". |
| I46 | Laatulaituri does not state whether its prices include VAT; they are treated as **including** VAT (the lower VAT 0 % price). Breaking loads published in tonnes ("n. 10 t") are converted × 9.81 kN/t. Chains without a published breaking load (A-Laiturit) stay in the list but are never chosen by the anchoring calculation. | Stated in each row's note. |
| I47 | **Anchoring method** (`engine/anchoring.ts`, docs/RESEARCH.md §5): wind on boats (lateral area = length × profile height, profile height = 0.25 × length, *assumption*) and on the pontoon freeboard; the windward row in full and the leeward row at 20 % (UFC 4-152-07); crossed chain pairs every 12 m (*assumption*) plus two axial lines at the head at ±30°; chain length = 3 × depth at high water (*assumption* between the suppliers' rules of thumb, 2 × and 5 × depth, Top Marine, and 3 × for open water, Suomen Laiturikauppa); exact catenary with uplift at the anchor when the chain does not reach the bottom; chain chosen by breaking load × ((d − c)/d)² ≥ 3 × top tension (c = 2 mm, *assumptions*); anchor submerged weight ≥ 1.5 × (H/μ + uplift), μ clay 0.3 / sand 0.6 / rock 0.5 (sand from Banuelos-Garcia et al. 2022, others *assumptions*). Every factor is a project parameter. | Transparent textbook mechanics; the paid standards could not be used (D15). |
| I48 | The first version required the chain to lie on the bottom at the design load; that gave chains of about 80 m for a 30 m pier. It was replaced by the rule-based chain length with uplift (I47). | Found in the sanity check against supplier practice. |
| I49 | **Known gap to practice:** with the defaults, anchors come out several tonnes per line, far heavier than suppliers' standard packages (2 × 1 000–3 000 kg per pontoon, Top Marine), whose design loads are not published. The tool does not tune its defaults to match; it shows the comparison next to the results and flags anchors outside the water and lines that need several anchors. | Honest result of stated assumptions; the owner can adjust wind, friction and spacing per site. |
| I50 | **Product choice:** pontoon and finger series closest in width to the layout's pier and finger widths (ties: lower price per metre); gangway series cheapest at `gangway_length_m`. The user can choose any series. Pontoon modules per pier: the cheapest combination of the series' lengths that covers the pier (≥ length − 0.05 m), ties fewer modules; the built length is reported when it exceeds the layout by more than 1 m. Fingers: the shortest product at least as long as the finger. | Deterministic and explainable. |
| I51 | **Gangways:** one per pier starting at the shoreline and one per access pontoon. **Fittings:** cleats per berth, ladders per pier, power pedestals per n berths (0 = none) from the price list's parameters. Per-metre pontoons (Marinetek estimate) count one module per 12 m for installation hours. | Parameters with "Assumption" as their source. |
| I52 | **Labour and plant** = quantities × output rates (h per unit) × rates of rows `rate-installer`, `rate-diving-team`, `rate-crane`, `rate-work-boat`. Order quantities: whole pieces; other units rounded to 0.1. Totals: subtotal × (1 + site overheads) × (1 + contingency); range −30 … +50 % (Class 4 as quoted for AACE 18R-97). | docs/RESEARCH.md §4. |
| I53 | The anchoring plan and the estimate are **derived data** (not stored): recomputed from the project and the price list when shown. An imported price list is stored in the project, so a project file keeps the prices it was estimated with. | Same rule as fairways and issues (U7). |

## User interface

| # | Decision | Why |
|---|---|---|
| U1 | A pier is dragged either along its axis or square to it; the direction is chosen by the first movement and kept until the mouse is released. Drags are rounded to 0.1 m. | SPEC §8: "drag a pier along its axis or laterally". |
| U2 | Removing a berth keeps its fingers. Locking a pier does not mark the layout as manually edited. | Fingers are structures; add/remove fingers is Phase 2. Locking changes no geometry. |
| U3 | After an edit the alternatives keep their order; scores are updated. Changing the objective re-ranks them. | A list that re-sorts under the cursor while dragging would be confusing. |
| U4 | A double-click is two clicks within 350 ms **and** 4 px. | Konva's built-in double-click ignores distance, so two quick clicks on different points ended a drawing. |
| U5 | Site vertices are edited with a separate "Edit points" tool: drag to move, drag a midpoint to insert, double-click to delete. | Keeps point handles out of the way when selecting piers and berths. |
| U6 | The shoreline and entrance tools snap to water vertices first, then to the nearest point on the water boundary (10 px). | They must lie on the boundary for piers to connect. |
| U7 | The project file stores the layouts' elements; fairways, issues and statistics are recomputed on load. | One source of truth; a file edited by hand cannot carry inconsistent statistics. |
| U8 | Autosave to `localStorage` is debounced (0.4 s). If the quota is exceeded the project is saved without the background image and the user is told once. | The quota is small (a few MB); the image stays in the session and in saved project files. The exact quota was not verified. |
| U9 | The background image is placed by its top-left corner, rotates about that corner, and cannot be dragged. Calibration rescales it about the first clicked point. | Minimal implementation of SPEC §3.2. |
| U10 | Generation runs on the main thread (0.7–0.9 s for the demos in Chromium). | Simplest; the engine is DOM-free and can move to a Web Worker unchanged if larger sites need it. |
| U11 | Issue messages come from the engine in English; the rest of the UI is translated. | Finnish may be partial in v1 (SPEC §2); full localisation is Phase 3. |
| U12 | PNG export is the canvas as shown, at 2× resolution, with scale bar, north arrow and disclaimer drawn on it. CSV decimals use a point and no thousands separators. | Exports must carry the disclaimer (SPEC §1) and be readable by spreadsheets. |
| U13 | The store is reachable as `window.__marina` for debugging and for the end-to-end test. | The canvas has no DOM elements to query. |
| U18 | "Add pier" draws a new empty pier in the selected alternative with two clicks (shore end first); it is then selected so its sides can be filled. | Same two-click pattern as the entrance. |
| U14 | **The drawing stays in local metres.** The map only stores the latitude and longitude of the local origin (`Project.map`). Nothing in the engine reads it; no distance or area is computed from latitude/longitude (SPEC §3). | Keeps the engine and every existing project unchanged. |
| U15 | **Map scale.** Tiles are in Web Mercator. They are scaled to ground metres with two factors taken at the origin, on the WGS 84 ellipsoid: east–west `cos φ / √(1 − e² sin² φ)`, north–south `(1 − e²) cos φ / (1 − e² sin² φ)^1.5`. | Web Mercator stretches the map by about 1/cos φ (×2 at 60° N) and slightly differently in the two directions. Checked against reference lengths at 60° N (1° of longitude 55 800 m, 1° of latitude 111 412 m): 5 cm over 450 m, under 0.2 m over 1.1 km. |
| U16 | **Choosing the place:** the user types "lat, lon" or pastes a link from openstreetmap.org or Google Maps. The place is put in the middle of the current view; existing drawings do not move. There is no place-name search. | A search would need a geocoding service with its own usage terms. |
| U17 | **Tile use** follows the OSM Tile Usage Policy: the standard HTTPS tile address, only tiles in view are requested (at most 64 per view, none ahead), the browser caches them by the server's headers, and "© OpenStreetMap contributors" is drawn on the canvas and therefore on PNG exports. The policy forbids heavy use; this is acceptable for a tool with a few users, not for a widely used service. | https://operations.osmfoundation.org/policies/tiles/ . The tile server sends `access-control-allow-origin: *` (checked 2026-11-13), which the PNG export needs. |
